# Actualización de recetas por tandas y optimización de compilación

Objetivo: actualizar las recetas desactualizadas de `~/proyectos/sprint` contra referencias externas (cports → aports → repology), regenerar checksums con `kiss c`, construir con `kiss b`, y exprimir el rendimiento de compilación con flags por paquete, ThinLTO, PGO y BOLT (este último añadido al build de LLVM), sin que el sistema se quede sin RAM ni se cuelgue.
Rama: `feature/recipe-updates-build-perf` (desde `feature/remove-dead-patches`).
Entrega: work-unit commits por tanda en la rama de feature. Push, PR y merge son decisiones del usuario.
Test runner: `sh test/kiss-patch-audit/run` y `sh test/kiss-patch-fail/run` como regresión base del repo; herramientas nuevas llevan su `test/<nombre>/run` hermético.

Aceptación: `kiss-outdated` se ejecuta por subdirectorio de categoría (`core`, `extra`, `xorg`, `python`, `test`) del repo `sprint`; cada receta actualizada pasa por `kiss c <pkg>` y se construye con `kiss b <pkg>`.

L20. Causa raiz del reinicio (2026-10-21): el registro persistente de este sistema es `/var/log/messages` (busybox syslog, no journal) y su rotado `messages.0` conserva el arranque anterior. Ahi esta la causa: `rustc: page allocation failure: order:0, mode:0xc0de0(GFP_KERNEL|...)` con `CPU: 4 UID: 1000 PID: 12922 Comm: rustc` y una traza en `shrink_folio_list` -> `folio_alloc_swap` -> fallo de asignacion. O sea: un `rustc` del usuario (UID 1000, en paralelo con el build de KISS que va como root) provoco la falta de memoria; **no hubo panic ni OOM-kill** (0 coincidencias), el kernel se quedo atascado en la via de recuperacion de memoria y el equipo se congelo hasta el reinicio forzado. En el momento del fallo habia ~40 MB de RAM libres pero 10 GB de swap "libres": como el swap es zram (RAM comprimida, no disco), no puede absorber la presion sin RAM, de ahi el atasco. El NVMe queda **exonerado** para este reinicio (cero errores de E/S en el log). Dos correcciones: (1) `earlyoom` no puede actuar con el zram vacio porque exige que memoria Y swap esten por debajo del minimo ("both memory and swap must be below minimum for earlyoom to act"), asi que nunca mataba a nadie: se le pasa `-s 100,100` (la condicion de swap queda trivialmente cierta y decide solo por RAM: SIGTERM bajo el 10% disponible, SIGKILL bajo el 5%); `-s 0` no vale porque earlyoom lo rechaza con "both SIGTERM and SIGKILL values are zero". Paquete `extra/earlyoom` subido a 1.9.0-3. (2) El build se relanza con `setsid` para que viva en su propia sesion y ningun signal de grupo lo alcance: el intento anterior murio con un SIGTERM externo al 22% de la pasada final. Ademas queda pendiente de aplicar por el usuario: no lanzar dos compilaciones pesadas a la vez (la de rust con la de LLVM fue exactamente eso).
